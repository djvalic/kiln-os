# Changelog

What changed for people using Kiln OS. Each release's notes (Gitea and
GitHub) take its section from here: `## vX.Y.Z (date)`, or `## Unreleased` when
the release has no section of its own yet. `tools/release.sh` renames
`## Unreleased` to the release's heading and starts a new empty one.

When an entry fixes a reported issue, add its number as `(issue #N)` in the
entry, so the GitHub release links to the issue. A release does not close
the issue: it is closed by hand after the release.

## Unreleased

## v1.0.1-rc2 (2026-11-25)

- **Community plugins** (plugin API 1.11): the plugin catalog can list plugins made by other people, in their own repositories. They are listed with their author's name and pinned: installing one from the catalog gives exactly the commit the catalog names, and `UPDATE_PLUGIN` moves only to the catalog's next commit, after automated checks (`tools/update_community_pins.py`; a change to a plugin's root scripts, submodules or Moonraker config is held for a person to read). A plugin you install by hand stays as before: not pinned, `UPDATE_PLUGIN` pulls, and its own update manager works in Fluidd. How to get a plugin listed: `docs/plugins.md` ("Community plugins"). happy-hare is listed this way, pinned to v4.1.0.5. On the touch screen, Settings > Plugins has two tabs, **Kiln OS** and **Community**: community plugins show who made them and a Root mark when they run scripts as root, a short note the first time the tab opens says they are made and supported by their authors, and the root question adds that root lets a plugin change system files. The whole Plugins screen is now in all 11 languages (it was English and Russian only).
- Installing a plugin no longer leaves a Moonraker warning ("file_manager: Error adding inotify watch to root 'config', path: .../plugins/.install-<name>/...") in Fluidd and on the printer screen: the plugin is cloned in `printer_data/plugin-staging/` and moved into `/data/ad5x/plugins/` in one step when complete, so Moonraker, which watches the plugins folder, no longer sees half-cloned folders vanish. Most likely with large plugins such as happy-hare.
- **Nozzle-hit guard** (new shipped plugin `nozzle-guard`, off by default): pauses the print when the nozzle hits the print or the bed. The bed weighing board is read 5 times a second during a print; a push over the limit (300 g by default; low / medium / high = 600 / 300 / 150 g) for 3 readings in a row pauses the print the way a filament runout does, the bed stays hot, and the touch screen shows the reason. It watches from the end of `PRINT_START`, not while homing or probing, during an IFS colour change or while paused. Turn it on in Settings > Safety & Alerts, or `ENABLE_PLUGIN NAME=nozzle-guard` and `NOZZLE_GUARD` (`docs/nozzle-guard.md`). The idea is zMod's `NOZZLE_CONTROL`, whose commands zmod-compat now maps to it; unlike zMod it never stops Klipper (which turns the bed off).
- **Plugin API 1.10**: the bed weighing board can be read in the background (`WEIGHT_MONITOR`, `printer.ad5x_weight` `force`, `peak`, `raw`, `baseline`, ..., the event `ad5x_weight:sample`), with a baseline that follows slow drift such as the bed heating.
- `Z_OFFSET_ESTIMATE` (off by default) uses the weighing board's measured scale, 56 raw counts per gram, instead of 43 (issue #94); its force limits are the same forces as before, now stated in true grams (300 g / 23 g).
- `Z_OFFSET_ESTIMATE` (off by default) no longer presses the nozzle into the bed when a bed mesh or Z offset is loaded, as one is after every print: it moved with ordinary G-code moves, which the mesh shifts, while the probe height it works from is not shifted. On a printer it went about 3 mm below where the probe fires and gave a wrong estimate (issue #94). It now moves in the probe's own coordinates and starts 1.2 mm above the trigger instead of 0.6, since plastic left on the nozzle can touch first. Measured with the nozzle hot and clean, the nozzle first touches the bed 0.2-0.25 mm above where the probe fires, close to the 0.25 mm `ad5x.cfg` assumes.
- **Belt Tension screen checked on an AD5X**: HelixScreen's Advanced > Belt Tension uses the toolhead accelerometer Kiln already drives; on the developer's printer both belt diagonals peaked at 52-53 Hz, inside Kiln's 20-80 Hz test range, and the accelerometer dropped no samples over its 500 kHz link.
- **Tailscale in the plugin catalog**: Settings > Plugins offers Tailscale (remote access): Fluidd and Moonraker from anywhere through your own Tailscale tailnet, with no ports opened on your router ([kiln-tailscale](https://github.com/djvalic/kiln-tailscale), Tailscale built from source for the AD5X). It needs Extended memory (a 512 MiB printer); measured on an AD5X: about 21 MB idle, up to 27 MB with Fluidd and the camera open remotely.

## v1.0.1-rc1 (2026-11-24)

**Kiln OS v1.0.1-rc1 is a release candidate for testers.** It's offered only to printers on the test channel; everyone else gets v1.0.1 once it's out. Everything below is new since v1.0.0.

- **Colour changes:** after the purge, the head now leaves the purge box the way the stock firmware does: the bed stays lowered while the head moves forward, then across, and the bed only comes back up once the head is over the print, so purge blobs no longer land on the back of the bed. The same for `M600` with the zmod-compat plugin.
- **OrcaSlicer:** Kiln profiles for every nozzle size, with process and filament profiles ([kiln-orca](https://github.com/djvalic/kiln-orca/releases/latest)), and OrcaSlicer's filament sync now picks them for each IFS slot.
- **Plugins:** Spool inventory (microspool, a spool server on the printer) is in the catalog. Settings > Plugins can switch on plugins that run code as root (it asks first). A plugin installed by hand shows up by itself. USB NFC card readers work for plugins without root, for spool-tag plugins such as FF_NFC.

**Please check these and tell us what you find, in #beta-testing on Discord or as a GitHub issue:**
- A print with 2 or more colours: no blobs on the back edge of the bed, and each colour starts cleanly after a change.
- If you use `M600`: the bed lowers before the head goes to the purge box, and the head comes back without dragging filament across the print.
- OrcaSlicer: import the profiles and print with them. If you try the prime tower with them, tell us how it went.
- Plugins: install Spool inventory from Settings > Plugins. If you have an NFC reader, try it with FF_NFC.

**To join the test channel** (from a computer on the same network): `curl -X POST 'http://PRINTER/machine/kiln_os/channel?channel=test'`, then refresh in Fluidd's Software Updates. `channel=stable` leaves it again; leaving never downgrades.

- **Purge blobs no longer land on the back of the bed after a colour change**: after the purge and wipe at the purge box, the head now leaves the box the way the stock firmware does. The bed stays lowered while the head moves straight forward, then across, and only comes back up once the head is over the spot where the print continues. Before, the bed came back up while the head was still leaving the box, so a blob still hanging from the nozzle could be dragged onto the back edge of the bed. Purge amounts and the wipe are unchanged.
- **The same for a filament change with `M600`** (zMod's command, with the zmod-compat plugin): the bed now lowers 50 mm, as on zMod, before the head goes to the purge box, and on Resume the head comes back the same way as after a colour change: forward, then across with the bed still lowered, and the bed only comes back up over the print. Before, the head waited at the box at print height and the bed came back up on the way, so filament purged by hand at the box could be dragged over the bed or the print. Pause and Resume from the screen or Fluidd, a runout and the IFS auto-refill move as before.
- **OrcaSlicer profiles that import, for every nozzle**: Kiln's OrcaSlicer profiles now live in [kiln-orca](https://github.com/djvalic/kiln-orca/releases/latest) (download the zip, File > Import > Import Configs): a printer profile per nozzle size (0.2-1.0 mm) with Kiln's G-code, process profiles, and a filament profile for each IFS slot material. The old ones in this repository didn't import (OrcaSlicer needs a version field they lacked) and left the tool-change retraction at OrcaSlicer's 10 mm; the new ones retract 3 mm and put the same 3 mm back, which undoes the printer's own pull-back after the purge. `docs/orcaslicer.md` now also says that OrcaSlicer's flush settings don't change the printer's purge, how to measure the purge (`IFS_PURGE_TEST`), that a painted top surface means a colour change on every top layer, and uses Flashforge's PLA temperatures (220 °C, bed 55/50).
- **OrcaSlicer's filament sync picks Kiln's filament profiles**: with OrcaSlicer 2.5's printer agent turned on (Preferences > Developer > "Use printer agents instead of print hosts", off by default), syncing the filaments from the printer now picks Kiln's own profile for each IFS slot (AD5X PLA, AD5X Silk PLA, AD5X PETG and so on), when the kiln-orca profiles are imported. Before, OrcaSlicer matched only the material name against its built-in profiles, so imported profiles were never chosen. Import the kiln-orca profile zip again after its next release: the older profiles don't carry the ids the printer now sends. A slot with a material you typed yourself is matched by name, as before. The printer and the touch screen no longer wipe each other's slot details: a slot linked to a Spoolman spool keeps its spool and, when the spool's filament names an OrcaSlicer profile, that profile, and only the slots that changed are written.
- **Settings > Plugins can switch on a plugin that runs code as root**: it asks first. Some plugins run part of their code as root, the system's administrator account, for example to set up USB devices. The touch screen's switch could not turn such a plugin on: Klipper refused the request and the switch went back, so only `ENABLE_PLUGIN NAME=... ROOT=1` in the console could turn it on. Now the switch shows a warning that says the plugin runs code as root and to turn it on only if you trust where it comes from; Turn On switches it on, and Klipper restarts once the plugin's root part is set up. A plugin like that installed from the catalog on the screen stays off until you switch it on this way. In every language of the touch screen.
- **Spool inventory in the plugin catalog**: Settings > Plugins on the touch screen (or `INSTALL_PLUGIN NAME=microspool ENABLE=1`) now offers Spool inventory, a spool server on the printer itself ([kiln-microspool](https://github.com/djvalic/kiln-microspool): microspool by sntgl, a small Spoolman-compatible server with a web page on port 7912). With the IFS, install Spoolman too, so each slot's spool counts its own prints.
- **A plugin installed by hand shows up on the touch screen by itself**: a plugin cloned over SSH into `/data/ad5x/plugins` wasn't listed in Settings > Plugins until `LIST_PLUGINS` was run or Klipper restarted. The list now notices a plugin added or removed by hand within a few seconds.
- **USB NFC card readers work for plugins without root**: a USB smart-card reader (ACR122U, ACR1552U and every other CCID/PC/SC reader) is now usable by the `klipper` user, so a plugin such as FF_NFC (spool tags) can drive it without a root part of its own. Only devices with a smart-card interface are opened this way; every other USB device keeps the default access. The kernels also have the driver for PL2303 USB serial adapters now, so those show up as `/dev/ttyUSB*` like CH340, CP210x and FTDI ones already do.
- Two leftover "experimental" mentions of Kiln's own boot loader are gone: the bench tools' README quoted the recovery screen's old button name, and the eMMC repair tool's message for a first MiB that would install Kiln's boot loader still called it experimental.
- Release tooling: a release can be built and tested once under its final name, kept aside, and published later with exactly those files, without a second build.
- Release tooling: the builder runs independent test steps at the same time, which shortens a full build and test run.

## v1.0.0 (2026-11-23)

**Kiln OS 1.0 is the first stable release.** From v1.0.0 on, every 1.x release keeps the plugin API (now 1.9), Kiln's web API, your config files and data, and the update and recovery path as they are, so plugins, slicer profiles, scripts and forks made for 1.0 keep working. A change that would break one of them waits for 2.0 ([what stays the same in 1.x](https://github.com/djvalic/kiln-os/blob/v1.0.0/docs/stability.md)). Kiln's own boot loader stays opt-in: it is offered only on known boards and asks twice before it installs ([boot loader guide](https://github.com/djvalic/kiln-os/blob/v1.0.0/docs/own-boot-loader.md)).

- **From v1.0.0-rc7:** the list below is everything that changed.
- **From v0.0.61, the last stable release:** this update also brings every change listed under v0.1.0-rc1 and v1.0.0-rc2 to rc7 in [CHANGELOG.md](https://github.com/djvalic/kiln-os/blob/v1.0.0/CHANGELOG.md). The biggest: Return to Flashforge firmware from the touch screen (Settings > System); NetworkManager runs Ethernet and Wi-Fi; a hung printer restarts by itself; bed screw levelling (`BED_LEVEL_SCREWS_TUNE`); the IFS buttons home the printer first; Happy Hare and git submodules for plugins; a rescue kit with every release; and Kiln's own boot loader as an opt-in from the recovery screen. One change you may notice: Kiln OS now uses 252 MiB of memory by default, also on printers with 512 MiB; Settings > System > Extended memory turns the rest on.
- **On the test channel:** a printer on a release candidate is offered v1.0.0 now. To get only stable releases from here on, switch back with `curl -X POST 'http://PRINTER/machine/kiln_os/channel?channel=stable'`. Switching back never downgrades.

- **Network Settings no longer says "Not connected" right after a Wi-Fi join that worked**: after you joined a network on the touch screen, the Wi-Fi line could stay at "Not connected" with no address, although the printer was connected (the network list showed it with a tick, and Fluidd answered on the new address). The screen read the Wi-Fi state from just before the join and was never told to look again. It now reads it after the join, so the network's name and address show at once. The setup wizard's Wi-Fi step had the same fault in its address line; it is fixed too.
- **A wrong Wi-Fi password says so**: when the network refused the password, the touch screen only said that the connection failed ("Connection failed. Check password." in Network Settings, "Connection failed: Connection failed" in the setup wizard), the same as for any other failure. It now says "Wrong password? The network did not accept it." in Network Settings, in the hidden-network dialog and in the setup wizard. Other failures still show their own reason. In every language of the touch screen.
- **The setup wizard no longer disappears when you put filament back into the IFS**: when a filament came out of the IFS during the wizard (for example during the IFS tuning) and you put it back, the touch screen opened the slot editor for the new spool over the wizard, and closing that editor hid the wizard for good: the home screen showed, the wizard could not be reached, and Settings > Printer > Run Setup Wizard did nothing until a restart. While the wizard is open, putting filament into a port no longer opens the slot editor (the wizard's own steps ask for the filament), nothing that closes over the wizard hides it any more, and Run Setup Wizard brings a running wizard back to the front.
- **The setup wizard's IFS tuning copes with a filament that comes out**: when a slot's filament came out of the IFS during the tuning, the step stopped with an error, and on the stock IFS firmware the printer could be left paused although nothing was printing. Putting the filament back fed it in, but the IFS error stayed. The tuning, and the filament step's search for the slot in the toolhead, now keep the toolhead's runout check off while they run (as they already did on the IFS's Klipper firmware); the tuning says "slot N: no filament at the IFS (did it come out?): put it back, then Retry", and saves nothing from the run it broke (before, it could save a wrong feed speed). Putting the filament back clears the error, and Retry tunes again from the start.
- **Kiln's own boot loader is no longer marked experimental**: the recovery screen's buttons are now **Install Kiln's boot loader** and **Update Kiln's boot loader**, without "(experimental)", and the main touch screen's notice names them the same way. Nothing else about it changed: it is still opt-in, offered only on known boards, asks twice and reads every step back, and its pages still say plainly that it has been proven on one printer so far and that a printer which doesn't start after it needs to be opened (J28 USB). On a board that isn't on the list, the recovery screen now also says where to help get it added: the boot loader guide's section "Is my printer one of the known boards?". In English and Russian, like the rest of the recovery screen.
- **Documentation brought up to date with the system**: the setup wizard guide no longer says the vibration step needs numpy that the image lacks (numpy has been in the image for a while) and counts the eleven AD5X steps; the config layout lists `macros/system.cfg` (the System buttons in Fluidd), says the setup wizard's Z offset step checks the centre only rather than meshing, and no longer lists a prime line setting `unretract` that is gone; the HelixScreen notes say Z offset changes from the screen, including baby-steps, are saved; the README and the install guide say the USB-stick install has been done on a printer, and the README gives zMod's licence correctly (Apache-2.0; its Klipper fork is GPL-3.0). The pages on booting, installing, recovery, updates, the plugin API, the web API and what stays the same in 1.x now describe Kiln's own boot loader, Return to Flashforge firmware and v1.0.0 as they are; the three serial console pages agree on measuring the header's voltage before connecting an adapter.
- The boot loader notice's log line now says "the same build as the disk: up to date" when the recovery OS carries the build that is already installed, instead of ending in "unknown".
- Release tooling: when Gitea refuses to create a release right after the tag push (HTTP 500, seen at v1.0.0-rc7), the release script waits and tries again, and uses a release it finds already made for the tag.

## v1.0.0-rc7 (2026-11-22)

- **Fluidd shows files it can't save as read-only** (issue #96): a plugin folder copied into `/data/ad5x/plugins` as root over SSH belongs to root, and Moonraker (user `klipper`) can't change its files. Fluidd still opened them for editing, but a save failed without any message and the file stayed unchanged. Moonraker now lists a file as read-only when it can't write the file or its folder, and a folder when it can't write into it, so Fluidd shows a lock and doesn't offer to save. `chown -R klipper:klipper /data/ad5x/plugins/<name>` makes such a plugin editable. Plugins kept up to date by Moonraker's update manager (the catalog's notify, timelapse, spoolman and happy-hare) are read-only in Fluidd as before, by design.
- **Return to Flashforge firmware puts Flashforge's own boot loader back by default**: on a printer with Kiln's own boot loader, going back used to remove only Kiln's second stage and keep Kiln's small first stage (SPL), unless you ticked "Also put back Flashforge's own boot loader". Now Flashforge's own boot loader goes back whenever the printer's saved copy of it (`boot.img`, on the printer, on the usershare partition or on a Kiln stick) is found: the box is ticked by default, and you can untick it to keep Kiln's SPL. When no saved copy is found, there is no box, and the page says plainly that Flashforge's own boot loader can't be put back because the printer's saved copy wasn't found; Flashforge's firmware works all the same, started by Kiln's SPL. The same goes for a return asked for from the main OS, a stick or over SSH (`ad5x-return-stock --keep-kiln-spl` keeps Kiln's SPL). A return that was stopped, for example by a power cut, goes on with the choice it started with, also one started by an older recovery. Printers with Flashforge's boot loader are not affected. Also in Russian.
- **The touch screen tells you when a boot loader update is waiting**: Kiln's own boot loader is only ever updated by hand on the recovery screen, which most people rarely open. When the printer has Kiln's boot loader and the recovery OS that came with an update carries a newer build of it, the main touch screen now says once: "A boot loader update is ready. To install it: Settings > System > Boot into recovery > Reboot / Power > Update Kiln's boot loader." On a printer that still has Flashforge's boot loader and whose board Kiln's boot loader supports, it says once, from the third start on, that Kiln OS has its own boot loader for this printer, how to install it, and to read the boot loader guide first. Both appear only when the printer is idle (not during the setup wizard, not while printing), close with OK, and don't come back (the update notice only for a newer build). Nothing is installed by them. In every language of the touch screen.
- **Boot into recovery is in every language**: Settings > System > Boot into recovery, its question, its description and its messages were English in every language but English and Russian. They are translated now in all of the touch screen's languages, and the boot loader notices name the row the way your language shows it.
- **The recovery screen no longer offers an older boot loader as an update**: when you go back to an older Kiln release, its recovery OS carries an older build of Kiln's boot loader than the one on the printer, and Reboot / Power used to offer it as "update available" with an Update button. The screen now tells newer from older by the builds' dates: a newer build is offered as before; with an older one the line says "installed, build X (this recovery carries an older build, Y)" and there is no Update button. Going back to the older build is still possible over SSH (`ad5x-bootloader-install --yes`, which says that it is a downgrade); the screen's Update refuses it. Also in Russian.
- **Install Kiln's boot loader no longer needs a file made over SSH**: the recovery screen's Reboot / Power page now offers Install Kiln's boot loader on every printer whose board is on the allowlist and doesn't have Kiln's boot loader yet. Until now it only appeared after `touch /data/ad5x/bootloader-offer.enable` over SSH; that file does nothing now. The install itself is unchanged: two confirmations, and every step is read back.
- **The recovery screen always says which boot loader the printer has** (issue #97): Reboot / Power showed nothing about the boot loader when there was nothing to install or update, which looked the same as the screen failing to read it. It now always has one line, for example "Kiln's boot loader: installed, build Nov 19 2026 - 08:31:00, up to date". It also says when an update is available (the Update button stays below it), when this recovery carries another build that isn't offered, when only Kiln's SPL is there, or that Flashforge's boot loader starts the printer. While the screen is still reading it at start-up it says "reading"; only when it really couldn't be read does it say so, in yellow. The line is for reading only; nothing happens when you tap it. Also in Russian.
- **The recovery screen in Russian no longer mixes in English reasons and update lines**: when Return to Flashforge firmware or Kiln's boot loader can't be done right now, the reason after "Not possible now:" was the tool's English text (for example "busy: start-up-actions"), and the home screen's "Last update" showed the English line of the update log. In Russian both are Russian now. The usual reasons (another job still running, an unfinished return, no Flashforge files, no or too old Kiln OS in slot B, too little free space and a few more) have their own text; any other reason says that a safety check failed and that Logs > This session has the details. The last update says when it was, whether it was installed or failed, and the file's name. In English the screen shows the tools' own text as before.
- **"Run the setup wizard?" is in every language**: the question after a reinstall over Flashforge's firmware was only in English and Russian, so in German and the other languages the screen showed an English question above translated Run and Skip buttons. It is now in all of the touch screen's languages. In Korean and Turkish, the "Cannot calibrate while printing" message (Run during a print) was English too; it is translated now.
- **Clearer Russian in two places**: the "Run the setup wizard?" question now says Flashforge's firmware may have changed the boards' firmware (it read as if the boards themselves had changed), and the recovery screen's last update line no longer depends on the grammatical gender of the update's name.

## v1.0.0-rc6 (2026-11-21)

- **Touch calibration works even when the saved calibration is damaged** (issue #90): with a damaged touch range saved, every tap landed on the top edge, so the touch calibration (from Settings or by holding the screen 10 seconds) could never finish. It now reads the taps with the touch screen's own range, so it always finishes; cancelling it keeps what was there. A saved range far outside what the touch screen can report is ignored at the start, and the touch calibration opens by itself.
- **The boot loader page shows the install's result after the restart**: at the first start through Kiln's boot loader, the recovery screen opened the page while its start-up actions were still running, checked at once, and showed "Not possible now: busy: start-up-actions" with Install greyed, instead of the result. The page now leads with the result: Kiln's boot loader is installed and this start came through it, or it is installed but this start didn't, with what to do. It waits for the start-up actions before it checks, then says "Kiln's boot loader is installed and up to date" with no Install button. Over SSH, `ad5x-bootloader-install` now says `result: already installed (this build)` (exit 0) when the printer already has this build's boot loader, even while another job runs, instead of refusing. Also in Russian.
- **Install Kiln's boot loader no longer calls a first install "stopped part-way"**: with a stock boot loader saved earlier and an empty U-Boot area (as Flashforge's factory reset leaves it), the check said "an earlier install stopped after part of the work", and the screen offered Continue, which skips the two confirmations. It now says "ready to install". An install really cut short (its record says so, or Kiln's SPL or part of its U-Boot is already on the printer) still goes on from where it stopped.
- **Settings and other long pages scroll with a finger drag again; the up/down arrows are easier to hit**: a drag on the rows of a Settings page (Printing, Devices, Safety & Alerts and the others) scrolls it again, and a tap on the arrows at the right edge pages even when the finger slips a little or lands between them.
- Docs: a pinout of the main board connectors, by alexshev86 (PR #92), with where J5 pins 13 and 19 go on the display board.
- Docs: a block diagram of the main board, and the bed weighing board's trigger to the probe input confirmed by a press test, by jolting (PR #93).
- Docs: the README says where to get help: bugs and feature requests as GitHub issues, questions and prints on the Kiln OS Discord.
- **A touch calibration that was converted twice is caught, and the screen asks for a new one**: a calibration made on Kiln's kernel before the settings recorded its units was taken for the stock kernel's units and converted again at the next start, so taps landed far off target or not at all. Kiln now checks the numbers: a calibration already in Kiln's units is kept as it is, and one that can't be right on either kernel (like the twice-converted one) is replaced with the calibration a fresh install starts with, so taps land roughly right, and the touch calibration opens by itself when the screen starts until you have calibrated again (issue #90).
- **A fresh install asks you to calibrate the touch screen at the first start**: the setup wizard now starts with the touch screen's calibration (tap the targets), so screens that read touches differently from the usual ones work too. Before, Kiln came with a ready-made calibration and the step was skipped; on some printers the touch screen then ignored every tap until it was calibrated in the settings, while the recovery screen worked (issue #90). Until you calibrate, taps map the way the recovery screen does. Printers already installed keep their calibration, and updates don't ask. The screen in the browser now also leaves out a calibration that isn't valid.
- **Hold the screen 10 seconds to calibrate the touch screen** (PR #91 by jolting, issue #90): if taps land in the wrong place, hold a finger still anywhere on the screen for 10 seconds and the touch calibration opens. In the setup wizard it goes back to the wizard's own touch calibration step; in Settings > Printer > Run Setup Wizard it ends that run first. An open dialog or the first-run tour is closed first (the tour comes back later). It does nothing on the lock screen, so it can't get past a PIN, or while a "please wait" or abort screen is up. The finger may lift for a moment or slip a little during the hold, but tapping is not a hold. Taps, long presses, scrolling and sliders work as before, but a 10 s hold on the jog pad or a slider opens the calibration too. Nothing happens on the calibration screen itself, and once it has opened, take your finger off the screen for 3 seconds before it can open again.
- **After a reinstall over Flashforge's firmware the touch screen offers the setup wizard**: Return to Flashforge firmware keeps your Kiln settings, and with them the record that the setup wizard was done, so a printer installed again from the install stick went straight to the home screen. Your settings are still kept, but at the first start the screen now asks "Run the setup wizard?", because the stock firmware may have changed the filament, the Z offset or the boards in between. **Run** starts the same wizard as Settings > Printer > Run Setup Wizard (every step can be skipped); **Skip** goes to the home screen and doesn't ask again. Also in Russian. Updates (Fluidd, `.swu`, recovery) never ask, and a printer without Kiln settings from before gets the wizard as a first run, as before.
- **Return to Flashforge firmware can remove Kiln OS's settings and files too**: the page has two new boxes, both off: **Also remove Kiln OS's settings and files** and, under it, **...and the uploaded print files too**. Ticked, Kiln's data on the printer (printer settings with the Z offset and mesh, network, plugins, SSH keys, logs, the screen's settings) is deleted once Flashforge's firmware is back and checked, so a later install of Kiln OS starts fresh with the setup wizard. Both confirmation steps say what is deleted, with its size, and that it can't be undone; the result says what was removed. Kiln's copy of Flashforge's own files, the return's log and (unless the second box is ticked) the print files stay; stock's own files and the usershare partition are never touched. If the return doesn't finish, nothing is deleted. Without the boxes nothing changes: your Kiln settings stay for a later install. Also in Russian.

- **Kiln's own boot loader sets the eMMC pins to 1.8 V on every start** (issue #68, found by jolting): the printer's eMMC runs its signals at 1.8 V. The chip's boot ROM sets its eMMC pins to that only when it starts from the eMMC, not in USB boot mode, so after a start over USB (J28) the pins were at 3.3 V: the eMMC still answered, but reads were unreliable and U-Boot couldn't read it at all. jolting measured it on printer 2: at 3.3 V only 4 of the 8 sample points read, at 1.8 V all 8. Kiln's SPL now sets 1.8 V itself before it touches the eMMC, U-Boot checks again before it reads, and each prints a line on the serial console when it had to change it. A normal start from the eMMC finds it set already and prints nothing.
- **U-Boot reads and writes the eMMC by DMA** (PR #81 by jolting): with U-Boot's network console on, reads of the eMMC sometimes came back with one wrong word while the bus check still passed, so a kernel could fail its checks and the printer fall back to the SPL's own start (4 of 20 reads wrong on jolting's printer). U-Boot now moves eMMC data by the controller's ADMA2, as Ingenic's driver and Linux do: 0 of 54 reads wrong, at the same speed.
- **Kiln's own boot loader reads more eMMC chips, and says why when it can't** (issue #68): eMMC chips differ between AD5X printers. When a read fails, Kiln's SPL now moves the eMMC sample point to the middle of its window and reads again, for any read and not only the first. If that fails too, it starts the eMMC again at the slow 400 kHz setting and boots that way (about 2 minutes slower). Started over USB (J28), it sets the eMMC clock the way the boot ROM does on a normal start before its first read. Each failed read prints which step failed and the eMMC controller's status on the serial console, and "can't read 0xA400" is now told apart from "no U-Boot at 0xA400".
- **The right delay-loop value for the X2600E** (issue #68): Kiln's SPL and U-Boot now give the kernel `lpj=11476992` on printers with the 256 MiB X2600E chip (measured by jolting there, and what Flashforge's 2025 boot loader passes) and keep `lpj=11935744` on the X2600H.
- **Boot loader build check matches memory tables by chip** (PR #74 by jolting): `check_first_mib.py` now compares Kiln's memory tables with the stock SPL's by DDR ID instead of by name. Printers with Flashforge's November 2025 boot loader are still refused.

- **Upgrading Kiln's own boot loader**: `ad5x-bootloader-install` (recovery OS) now also upgrades a Kiln boot loader of another build, from an earlier install or the bench tools, to the one the recovery OS carries. It writes the new SPL first, then U-Boot up to the old one's end, keeps U-Boot's settings and records, and saves the old first MiB in `/data/ad5x/bootloader/before-upgrade.img`. `--status` shows both builds, and `--offer` adds `bootloader_upgrade=yes|no`. Before this it refused with "updating it isn't supported yet".
- **Extended memory with an older Kiln boot loader**: a printer started by a Kiln U-Boot from before the memory mode (such as the rc3 opt-in boot loader) can't switch modes until the boot loader is upgraded. `ad5x-memory status` says `bootloader_update_needed=1` instead of asking for a restart, Kiln's API adds `bootloader_update_needed` and no longer offers a restart or the notice, and the touch screen's Extended memory row says "Needs a boot loader update to take effect." The switch can still be set and counts after the upgrade.

- **Reboot and Shutdown on the touch screen ask only what you tapped**: under Advanced > Power, Reboot now asks "Restart the printer?" (Restart or Cancel) and Shutdown asks "Shut down the printer?" (Shutdown or Cancel), instead of both opening the same dialog with both choices. Both still go through Kiln's update agent, which refuses while a print runs and says why, and a short message now says when the printer accepted. The home screen's power tile keeps the dialog with both choices.
- **Extended memory, for printers with 512 MiB** (issue #68): every AD5X now runs the same: Kiln OS uses the low 252 MiB of memory by default, also on printers that have 512 MiB. On a printer with 512 MiB you can switch **Extended memory** on under Settings > System on the touch screen (or `KILN_MEMORY_MODE ENABLE=1` in the console, `POST /machine/kiln_os/memory?enable=true`, or `ad5x-memory extended on` over SSH) to use all of it from the next start. It isn't needed, it is off by default, and it stays as you set it across restarts and updates. **Printers with 512 MiB that run v1.0.0-rc3 used all of it until now; after this update they run in standard memory until you switch Extended memory on.** A one-time notice under the touch screen's bell (and in Fluidd and Mainsail's announcements) says so on those printers. The first start with Extended memory tests the upper 256 MiB once (a few seconds); if that test finds a fault, or a start with Extended memory doesn't finish, the printer switches it off by itself and starts in standard memory, and the touch screen says why. The recovery OS always runs in standard memory. With Kiln's own boot loader, U-Boot follows the same switch and counts a failed start with Extended memory as one of its tries. For developers: Kiln's kernels get `ad5x.ram=256|512 ad5x.memmode=standard|extended` on the command line, `/run/ad5x-memory.conf` has `HW_MEM_MIB` and `MEM_MODE`, the 6.6 kernel has `/proc/<pid>/pagemap` for the memory test, and the Kiln API is now 1.8 (`GET`/`POST /machine/kiln_os/memory`, `POST /machine/kiln_os/memory_notice_seen`, feature `memory_mode`; `docs/api.md`). The boot loader installer and Return to Flashforge firmware still recognise an X2600H in standard memory as an X2600H. `docs/memory.md` has the details.
- **The update agent clears a leftover "Return to Flashforge firmware" request at its start**, as it already did for the other requests.
- **No more "Overcurrent change detected" flood on the 7.3 kernel** (issue #82, reported by alexshev86): on the opt-in 7.3 kernel the USB port on the board's J28 footprint (the chip's USB boot connector, which has no power switch) reported a false overcurrent many times a second, with or without anything connected, filling the kernel log and rotating the system log about every 90 seconds. The port could also stay switched off, so a USB device plugged in there wasn't reachable. Its overcurrent detection is now off, as on the other USB port and in the stock firmware.
- **Kiln's own boot loader works on both AD5X chips** (PR #74 by jolting, issue #68): jolting found that the AD5X ships with two versions of its X2600 chip: the X2600H with 512 MiB of DDR3L memory and the X2600E with 256 MiB of DDR3, and that you can't tell which one a printer has from the outside. Kiln's SPL now reads the chip type from the chip's eFuse at power-on and sets up the memory for it, so one boot loader image works on both. Anything it can't read or doesn't expect gets the X2600H settings, exactly as before. On a 256 MiB printer neither the SPL nor U-Boot tells the kernel about a second memory bank it doesn't have. If the very first eMMC read fails its data check, the SPL tries once more with a different read timing (jolting's X2600E needed it over USB); printers that read fine see no change. The serial console says which chip and memory table it used (`SPL: SoC ID 38200 (variant 3), DDR ID 84`). Because it has not yet started from an X2600E's eMMC, the installer offers it on X2600E printers only over SSH with `--unsupported-board`, at your own risk, never on the touch screen.
- **The boot loader installer checks the chip** (issue #68): Install Kiln's boot loader now tells the chip from the memory size: an X2600H goes on as before, an X2600E only over SSH with `--unsupported-board` and the typed confirmation, and a printer where it can't tell is refused even with `--unsupported-board`, before anything is asked or written. The board fingerprint finds the memory tables by name, so printers with Flashforge's November 2025 boot loader (build 00437, on both chips) get a correct fingerprint, and it now shows the chip and the memory size. Return to Flashforge firmware can put Flashforge's own boot loader back on those printers too. The first install writes the chip and memory size into the install log.
- **Kiln OS on printers with 256 MiB of memory** (issue #68): Kiln OS now sets itself up at each start for the memory the printer has. On every printer the RAM folders `/tmp`, `/run` and `/dev/shm` have a size limit, so one of them filling up can't take the memory Klipper needs, and Moonraker keeps uploads on the data partition while they arrive instead of in RAM. When memory runs out, the camera is stopped first and Klipper last, so a print keeps going. On printers with less than about 300 MB, Kiln OS also adds 64 MiB of compressed swap in RAM (zram) and the camera uses fewer buffers. The recovery OS unpacks updates on the data partition instead of in RAM when there is room. Both kernels now report memory pressure in `/proc/pressure`. `docs/memory.md` has the details.
- **16 MiB more memory for Kiln OS, and leaner kernels** (issue #68): Kiln's 6.6 and 7.3 kernels now get the low 252 MiB of memory instead of the 236 MiB the stock firmware gives its own kernel, which kept 16 MiB back for Ingenic media drivers that Kiln OS doesn't use. This works the same with Flashforge's boot loader and with Kiln's own; the stock kernel still gets its own settings. The kernel crash log moved to the top of that area and shrank to 256 KiB, so the stock kernel's start on the way to Kiln's no longer overwrites it. Both kernels no longer load modules (nothing used them), carry only the USB webcam media drivers, and keep a smaller log buffer and display memory area; the 7.3 kernel also drops io_uring and its full symbol table, and uses about 1.5 MiB less memory.
- **Less memory for Moonraker and the touch screen, and Klipper kept in RAM** (issue #68): Moonraker and the touch screen now use at most two glibc memory pools instead of one per thread, which saves a few MiB. Moonraker no longer loads its D-Bus library or tries to connect when the system has no D-Bus (the "Unable to Connect to D-Bus" line in moonraker.log is gone), and the unused cron service is no longer in the system. Klipper now locks its memory in RAM, so memory pressure (and the compressed swap on 256 MiB printers) can't slow it down mid-print; the klippy.log line `ad5x_mlock:` says whether it worked. `touch /data/ad5x/klipper-mlock.disable` turns it off at Klipper's next start.
- **Kiln's own boot loader: a printer with nothing left to start waits in USB boot mode by itself** (thanks to alexshev86's tests 1 and 4, issue #68): alexshev86 found that with the SPL's header zeroed the chip goes into USB boot mode by itself (test 1), but with both kernel slots' headers zeroed Flashforge's SPL just hangs, and only a K4 short gets the chip into USB mode (test 4). Kiln's SPL no longer stops in that case: when its four tries (U-Boot, then each kernel slot) start nothing, it asks the chip's boot ROM for its USB mode, the same request as the soft entry alexshev86 found, and restarts into it. The printer then shows up on the white J28 USB connector as `a108:eaef`, ready for a restore with USBCloner, without K4. The serial console says `nothing started after 4 attempts ...: boot ROM USB mode (J28)`. Switching the power off and on still tries a normal start from the eMMC first (the request doesn't survive a power cut), and goes back to USB mode after the four tries if still nothing starts. If the boot ROM ever ignores the request and starts from the eMMC anyway, the SPL stops on that start, as it did before. This only matters on printers with Kiln's own boot loader installed; `docs/own-boot-loader.md` ("If nothing starts") has the details.

## v1.0.0-rc3 (2026-11-16)

- **Safer boot loader writes, and boards restored over USB recognised** (thanks to alexshev86's broken-SPL test, issue #68): alexshev86 zeroed the SPL's header sector on his AD5X on purpose and found that the boot ROM then goes into USB boot mode by itself, with no K4 short, and that the board comes back with Ingenic's USBCloner over J28 writing its own first MiB back. Kiln OS now uses that: the installer, Return to Flashforge firmware (with Flashforge's boot loader) and the bench tool `ad5x-spl-flash` zero the SPL's header sector first, write the rest of the SPL and the length, and write the header sector last, each read back. A power cut at any moment of that write leaves the old SPL, the new SPL, or no SPL at all (USB boot mode), never a header in front of half an SPL, which would start a broken SPL and need the printer opened and K4 shorted. Two things from his restored board are handled too: USBCloner writes its DDR type into 4 bytes of the SPL header (0x4480) that no SPL reads, which changed the board fingerprint, so the fingerprint now reads those bytes as zeros (the known boards' fingerprints stay the same, and the snippet in `docs/own-boot-loader.md` is updated); and his board keeps its GPT's partition entries at sector 32 rather than 2, which made `ad5x-restore boot`, the installer and Return to Flashforge firmware refuse its own saved first MiB. After a review against the stock boot loader: the SPL arms its watchdog before anything that could hang, opens the serial port's clock and never waits on it for ever, sets the eMMC clock as the stock one does, and after a failure always tries the other slot instead of going round in circles; U-Boot hands over to the SPL instead of waiting at a prompt nobody sees, and stops at its prompt only for Ctrl-C or `kiln`; the first-MiB check refuses a printer whose stock boot loader has other memory or clock values, and the write plan touches only the boot loader's bytes. - **Kiln OS update right after a new release no longer shows a timeout**: pressing Update in Fluidd while the printer was still writing the new recovery OS (a few minutes after a new release first starts) showed "the update agent didn't answer" although the printer then installed the update anyway. It is now refused at once with "the recovery OS is being written into slot A, try again in a few minutes", and nothing happens.
- **A forgotten update no longer installs by surprise**: an update that was staged but never installed (for example when the printer lost power between staging and its restart) stayed in place and was installed the next time the recovery OS started, maybe much later and for another reason. When the printer starts normally, such an update is now set aside (renamed `.stale`) and never installed without being asked again (`docs/updates.md`, "Staged updates").
- **Update time**: Fluidd's message after staging a Kiln OS update now says the printer takes 3-6 minutes to install it and start again (it said about 3 minutes, which was often too short).
- **Touch calibration stays right after a screen reset**: calibrating the touch screen on Kiln's own kernel after a reset of the touch screen's settings could leave touches landing in the wrong place after the next restart, because the calibration was converted a second time. The touch screen now records which kernel's units each calibration is in.

The plugin is maintained in its author's repository; updates come through Fluidd.
- **Fixed names for USB boards, eudev in place of mdev** (PR #64 and #65 by jolting): Kiln OS now sets up `/dev` with eudev, the device manager most Linux systems use, in the main OS and the recovery OS. Each USB serial board (a toolhead board such as the EBB42, a probe, an accelerometer) now also gets a fixed name under `/dev/serial/by-id/`, so `serial:` in its `[mcu]` section can name the board itself instead of `/dev/ttyACM0`, which can change when a second board is plugged in; the board guides for other Klipper printers work as written. Network interfaces keep the names `eth0` and `wlan0`, and Klipper's user keeps its ids, so files in `/data` keep their owner across the update. The kernel no longer sets up the chip's H.264 video decoder, which nothing on the printer uses (the camera sends MJPEG): its driver crashed the kernel whenever a program opened it, and eudev looks at every video device at start-up. Thank you, jolting.

- **Boards are flashed with Kiln OS's own tools** (issue #20, PR #32 by Hunter Laux): `ad5x-flash-n32` (mainboard) and `ad5x-flash-iap` (eboard and IFS) replace Flashforge's closed binaries. The mainboard flasher reads the chip's ISP reply (boot version, UCID, UID) before it erases, refuses firmware larger than 512 KB, and pulses reset after a failed attempt. The mainboard's UID is pinned after its first verified flash (`mainboard.uid`); a later flash refuses to write if the chip's UID differs, so a board swap is not flashed by mistake. The eboard is started with `A` after its image is written (its bootloader stays waiting without it), and a flash that does not report the application started is counted as failed. The IFS gets nothing after its image, as with stock `IFSCommand`: its bootloader starts the application itself.

The old IFS build sat in its bootloader: its stack pointer failed the bootloader's check. Tested on a printer: Klipper ready with the IFS as a Klipper MCU, selector homing and a feeder move.

- **IFS as a Klipper MCU: a load with no toolhead sensor stops at the length limit** (IFS Klipper mode, not in this release): the feeder has no stall detection, so without `head_sensor` a load used to run its full length and report success. It now fails with an error at `load_length`, and a warning at start says so.
- **IFS as a Klipper MCU: a selector that does not find its endstop fails the load** (IFS Klipper mode, not in this release): the homing error names the endstop, and the selector motor is switched off. Before, the G-code error escaped without a reset.
- **IFS as a Klipper MCU: a stop during the wait for queued moves is kept** (IFS Klipper mode, not in this release; not yet covered by a test): IFS_STOP pressed while an earlier move still runs is no longer cleared before the next command starts. **IFS errors name a failed reset**, in both modes: after an error the reset runs (F15 on the serial link, the motors off in MCU mode); if it fails, the error says so instead of hiding it.

  the centre's (where the Z check probes), with the slowest corner's
  alongside.
- zMod's `START_PRINT` (zMod-sliced files) passes `SOAK=` on to
  `PRINT_START`; the soak applied to those files already.
- A cooler bed than the calibrated one never soaks longer than measured
  (a 55 °C PLA print after the 60 °C calibration: 420 s, not 565 s).
- A bed temperature without its own calibration uses the nearest one,
  scaled by how far the bed heats (an 80 C PETG print after a 60 C
  calibration soaks longer, not shorter); at most 10 minutes.

### Added

  (Notifications, Timelapse, Spoolman). No SSH, no reboot: Moonraker
  restarts by itself when needed. Console: `INSTALL_PLUGIN NAME=`,
  `UPDATE_PLUGIN`, `REMOVE_PLUGIN` (plugin API 1.4).

### Changed
- **Bed heat soak** before the Z check: the bed waits a little after
  reaching its temperature when it started cold, so the plate has stopped
  growing when Z is measured; the purge and brushing count. How long:
  measured on your printer with `BED_SOAK_CALIBRATE BED=80` (probes the
  centre and corners until they stop moving, saved per temperature), else
  3 s per degree the bed rose, at most 10 minutes. Optional "probe until
  stable" mode; `PRINT_START SOAK=` overrides; settings in the printer's
  `macros/print_start.cfg`.

## v0.0.5

### Added
- **Power-loss recovery.** While printing, the print's state is saved every
  10 s. After a power cut, `RESUME_INTERRUPTED CONFIRM=1` continues the
  print where it stopped (no Z homing into the part); `CLEAR_INTERRUPTED`
  forgets it.
- **IFS auto-refill** (off by default, `IFS_AUTO_REFILL ENABLE=1`): when a
  slot runs out mid-print, the printer switches to another slot with the
  same material and colour and carries on.
- **OrcaSlicer filament sync:** the IFS slots (material, colour,
  temperature) appear in Moonraker's `lane_data`, which OrcaSlicer's
  Moonraker printer agent reads. See docs/orcaslicer.md.
- **Spoolman plugin** (shipped, off): a Spoolman spool per IFS slot; the
  loaded slot's spool becomes the active one.
- **Recovery OS updates itself** together with the main OS.
- Releases publish their source code (GPL).

### Changed
- Starts about 20 s faster (11.6 s from start-up to ready, was 33 s).
- The clock starts at the last known time instead of 1970 until the
  network time is there.
- Smaller image (79 MB, was 92 MB): Python libraries as bytecode only.
- HelixScreen v1.1.0-beta.10.
- Klipper's `PID_CALIBRATE` now suggests about half the values it used
  to (an upstream fix). If temperatures oscillate, run the PID step again.
